# Mobile React Native migration assessment — 2026-10-20

This assessment defines the next Epic 4 dependency work. It does not change the app or establish that an npm advisory is exploitable on a shipped device. The 2026-10-19 [audit snapshot](mobile-dependency-audit-2026-10-19.md) recorded 34 production-graph findings (six moderate, 28 high, zero critical) after [PR #52](https://github.com/matthewubacbrian-afk/geohazard-ph/pull/52). npm proposed React Native 0.88.0 for 27 chain entries and marked seven `fixAvailable: true`; those entries are not 34 distinct vulnerable modules. Two fresh `npm audit --omit=dev --package-lock-only --json` attempts on Windows on 2026-10-20 returned no output before they were stopped, including one with a 10-second fetch timeout and no fetch retries. Re-run the audit on a clean CI runner before relying on a newer count.

## What the findings do and do not prove

The lockfile and npm's `--omit=dev` graph still include transitive CLI, code-generation, test, and Metro packages because React Native depends on tools used to build an app. Those names suggest build-time roles, but package names alone do not prove their absence from native runtime code. React Native itself is the runtime framework, and native libraries are linked into the app; their compatibility needs actual build and device evidence. The retained `image-size` 1.2.1 comes through Metro, which requests `^1.0.2`; the patched 2.0.4 line crosses a major API boundary. The [recorded advisories](mobile-dependency-audit-2026-10-19.md#remaining-findings-and-action) and dependency paths justify investigation, not a forced override or a claim of exploitability.

The first release-evidence slice below records whether each npm-reported package name appears in a production Hermes source map and lists selected packaged native files. It keeps every advisory disposition **undetermined**. A separate per-advisory review must still record each advisory identifier and affected version, the shortest lockfile dependency path, affected-API use or lack of evidence, and source links before classifying an item as **build tooling** or **packaged runtime**. Even a packaged item needs an attack-path assessment before a risk conclusion. Preserve only small manifests/reports, never generated app binaries or raw audit JSON in Git.

## Upstream constraints and target

- [React Native 0.76](https://reactnative.dev/blog/2024/10/23/release-0.76-new-architecture) makes the New Architecture the default and raises the minimum from Android SDK 23 to 24 and iOS 13.4 to 15.1. This is a supported-device policy change that the project has not approved with device evidence.
- [React Native 0.78](https://reactnative.dev/blog/2025/02/19/react-native-0.78) moves to React 19; it is not a framework-only version bump.
- [React Native 0.81](https://reactnative.dev/blog/2025/08/12/react-native-0.81) requires Node 20.19.4+ and Xcode 16.1+, and its Android template targets API 36. [React Native 0.82](https://reactnative.dev/blog/2025/10/08/react-native-0.82) is New-Architecture-only and recommends verifying that architecture on 0.81 first.
- [React Native 0.84](https://reactnative.dev/blog/2026/02/11/react-native-0.84) defaults to Hermes V1 and precompiled iOS binaries and requires Node 22.11+. [React Native 0.85](https://reactnative.dev/blog/2026/04/07/react-native-0.85) moves the Jest preset to `@react-native/jest-preset`.
- [React Native 0.87](https://reactnative.dev/blog/2026/08/11/react-native-0.87) makes strict TypeScript APIs the default, uses Metro 0.87, and requires Node 22.13.0+, Kotlin 2.0+, and Android compile/build tools 37. Its Android Gradle Plugin 9 guidance includes temporary built-in-Kotlin and DSL opt-outs. [React Native 0.88](https://reactnative.dev/blog/2026/10/19/react-native-0.88) is the latest stable release as of this assessment, with React 19.3.0 and Metro at least 0.87.1. Its claim of no *0.87-to-0.88* user-facing breaking changes does not describe this project's 0.75-to-0.88 migration.
- The [React Native Upgrade Helper workflow](https://reactnative.dev/docs/upgrading) compares native template files as well as JavaScript dependencies. Use its 0.75-to-candidate diffs, not package-manager output alone.

The target is a supported 0.88.x release, but treat the exact patch and companion library versions as a decision made from a fresh lockfile, upstream compatibility notes, and green builds when that implementation starts. Do not merge an unsupported 0.81 intermediate as the final dependency state. Use 0.81 as an internal New Architecture checkpoint within the migration branch if the direct template diff cannot be validated safely. CocoaPods remains supported in 0.88; adopting experimental Swift Package Manager is out of scope.

## Prioritized, shippable features

1. **Release-artifact exposure record on 0.75.5.** Add a reproducible CI or script path that builds a non-published Android release artifact and inspects the Hermes bundle and packaged native contents, plus an equivalent iOS simulator artifact where available. Link advisory paths to observed contents; keep the risk label `undetermined` when only a package-name check exists. Run the full package suites and native CI. This can merge without changing runtime behavior. It does not replace a security review of actual input paths.

   The focused [artifact-exposure plan](superpowers/plans/2026-10-20-mobile-artifact-exposure.md) tracks this implementation. The [dated evidence record](mobile-artifact-evidence-2026-10-20.md) captures clean CI reports and the corrected iOS inventory. The automated observation is the first step of the separate per-advisory review, not its conclusion.

2. **New Architecture readiness on the current framework.** Check the three native libraries' pinned-version support, update them in bounded dependency changes only where required, then enable the New Architecture for Android and iOS. Verify Jest, TypeScript, Android and iOS clean builds, plus saved-location persistence, SVG rendering, and image capture on real devices using the [runtime checklist](mobile-runtime-smoke-test.md). If devices are unavailable, CI readiness can merge but Epic 4 device acceptance remains open; do not claim runtime compatibility from builds alone.
3. **Supported React Native migration.** After recording the Android SDK 24/iOS 15.1 support-floor decision, update React Native, React, Metro config, native templates, Gradle/SDK/Kotlin, Pods, Jest preset, and any incompatible direct native libraries as one coherent framework change. Pin exact companion versions; use the Upgrade Helper and make the 0.81 New Architecture checkpoint within the branch if needed. Confirm the supported 0.88.x target and rerun the audit, every package suite and linter, Android/iOS debug and release builds, and artifact inspection. Require physical-device foreground/cache/camera flows before a production release. A clean CI build is necessary for merge but does not waive that release gate.
4. **Post-migration advisory disposition and device evidence.** Compare before/after advisory paths and artifacts, document any residual reachable issue or justified build-only classification, and record the Android/iOS runtime checklist with OS/device/app commit. Keep background push, signing, and store publication outside current Epic 4 scope.

Each feature gets a separate plan, worktree/branch, tests appropriate to its change, independent review, PR, and passing checks before merge. The first two can proceed without deciding to drop older operating systems. The framework migration cannot be called release-ready until the minimum-OS decision and real-device evidence are recorded. No existing host, test device, or approval is inferred from this assessment.

For each code-changing slice, a failed clean build, regression test, or verified device flow stops its PR before merge; fix in its branch or abandon that branch. If a merged migration later fails a required device flow, revert that migration PR and rebuild from the last verified main commit before distributing a new app. Record the failing OS/device and app commit in the runtime checklist; do not label a simulator-only build as release evidence.
