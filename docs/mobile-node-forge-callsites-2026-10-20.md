# Mobile `node-forge` consumer calls — 2026-10-20

This bounded review concerns [GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv), which affects RSA PKCS#1 v1.5 signature verification in `node-forge` through 1.4.0 when a crafted signature has extra nested `DigestAlgorithm` elements and a low-exponent key. It does not establish release reachability or change any of the 34 Android/iOS audit finding dispositions from **undetermined**.

## Pinned path and source

The production lockfile tree reads `react-native` 0.75.5 > `@react-native/community-cli-plugin` 0.75.5 > `@react-native/dev-middleware` 0.75.5 > `selfsigned` 2.4.1 > `node-forge` 1.4.0. This is a dependency path, not an execution trace. The published tarballs for the last three packages were checked against their `mobile/package-lock.json` SHA-512 integrity values before inspection. The [published middleware package](https://registry.npmjs.org/@react-native/dev-middleware/-/dev-middleware-0.75.5.tgz) declares `selfsigned ^2.4.1`, but a search of all 17 published `dist/**/*.js` files found no direct `selfsigned` or `node-forge` import or call. That result is limited to this exact package's distributed JavaScript; it does not prove that no other caller can load `selfsigned`.

| Consumer | Observed call and input origin | Relationship to advisory and limit |
| --- | --- | --- |
| [`selfsigned` 2.4.1 `index.js`, `generate`](https://github.com/jfromaniello/selfsigned/blob/v2.4.1/index.js) | Requires `node-forge`; generates an RSA key pair by default or parses caller-provided PEM keys via `options.keyPair`. It creates and signs a certificate, adds that certificate to a CA store, and calls `forge.pki.verifyCertificateChain(caStore, [cert], callback)`. | This is a **verification call**, not only key/certificate generation. [`node-forge` 1.4.0 `x509.js`](https://github.com/digitalbazaar/forge/blob/v1.4.0/lib/x509.js) can reach `parent.verify(cert)` from the chain verifier. Here the certificate being checked was constructed in this `generate` call. The published middleware has no observed call to `generate`; no path carrying a crafted external signature or low-exponent key into this call was established. |
| `@react-native/dev-middleware` 0.75.5 published `dist/**/*.js` | No direct import or call of `selfsigned` or `node-forge` in the 17 JavaScript files; the dependency appears in its manifest. | The lockfile edge alone does not demonstrate execution of the affected verification operation in Metro, a Release build, or a device. |

In the synchronous path, `options.keyPair` lets a caller supply keys to `selfsigned.generate`; the default generated key path and the optional key path should not be conflated. Neither the optional interface nor the internal certificate verification proves an attacker-controlled malformed signature reaches the vulnerable parser. A search for indirect loading, other `node-forge` consumers, and complete bundled/native attribution remains outside this slice. The Release source maps and inventories recorded in [artifact evidence](mobile-artifact-evidence-2026-10-20.md) also cannot settle those questions.

## Reproduction and next evidence

From `mobile/`, `npm ls node-forge selfsigned @react-native/dev-middleware --omit=dev --package-lock-only --all --json` reproduces the lockfile path without an install. Compare package tarball SHA-512 digests with their lockfile `integrity` values, then search the exact published middleware `dist/**/*.js` and inspect the published `selfsigned/index.js`. A future attack-path review must establish an actual caller, input provenance, vulnerable verification preconditions, and build/device inclusion before assigning any advisory disposition. Repeat that review after the supported React Native migration.
