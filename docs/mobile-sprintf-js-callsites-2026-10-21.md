# Mobile `sprintf-js` consumer calls — 2026-10-21

This bounded review concerns [GHSA-hp3w-g68c-fv3c](https://github.com/advisories/GHSA-hp3w-g68c-fv3c): `sprintf-js` through 1.1.3 accepts an out-of-range precision in an attacker-controlled numeric format string and passes it to `toFixed`, `toExponential`, or `toPrecision`, which can throw `RangeError`. The pinned mobile production lockfile contains `sprintf-js` 1.0.3. This review traces published calls in its observed dependency chain; it does not establish an end-to-end attack path or device-runtime use. The final [PR #60](https://github.com/matthewubacbrian-afk/geohazard-ph/pull/60) Android/iOS Release reports still contain 34 audit-chain findings each, all **undetermined**.

## Exact sources and dependency paths

`mobile/package-lock.json` has one installed `sprintf-js` copy, 1.0.3, directly declared only by `argparse` 1.0.10. The production chain recorded in the [advisory path review](mobile-advisory-exposure-review-2026-10-20.md) continues through top-level `js-yaml` 3.15.2 and Metro's nested `cosmiconfig` 5.2.1 to `metro-config` 0.80.12. A distinct `@react-native-community/cli-config` path uses top-level `cosmiconfig` 9.0.2, its nested `js-yaml` 4.3.2, and `argparse` 2.0.1; that parser does not declare `sprintf-js`. These are lockfile edges, not proof that the affected formatter executes. Published tarballs for all nine inspected packages were checked against their lockfile SHA-512 integrity values before inspection.

The pinned [`sprintf-js` source](https://registry.npmjs.org/sprintf-js/-/sprintf-js-1.0.3.tgz) parses numeric precision from the format string and passes it to `toExponential`, `toFixed`, or `toPrecision` without a range check. A local call against that exact source with `sprintf('%.101f', 1.2)` produced `RangeError: toFixed() digits argument must be between 0 and 100`. That confirms the affected operation; it says nothing about who controls a format string in this project.

A different parser caller or indirect path has not been ruled out. |

| `js-yaml` 3.15.2 `bin/js-yaml.js` creates an `ArgumentParser` | Fixed program name and option help strings; YAML file/stdin contents are read after argument parsing. | This separate command-line entry point imports `argparse`. This inspected YAML-load route does not pass file content to `sprintf-js`. |

The `js-yaml` package declares `argparse` because its published `bin/js-yaml.js` uses it; the published `lib/js-yaml.js` does not import it. The shortest Metro configuration dependency path therefore overstates executable reachability if read as a function-call chain. This review does not exclude another process invoking the YAML CLI, another consumer constructing a parser with an untrusted numeric format string, or behavior outside the inspected published files. The Release source-map and native-file inventories also cannot establish that `sprintf-js` runs in the distributed Android or iOS app. The advisory and all 34 audit finding dispositions remain **undetermined** pending the broader input and execution-path review.

## Reproduction

From `mobile/`, run `npm ls sprintf-js argparse js-yaml cosmiconfig metro-config --omit=dev --package-lock-only --all --json`. Compare each inspected published tarball's SHA-512 digest with `mobile/package-lock.json`, then inspect `sprintf-js/src/sprintf.js`, `argparse/lib/help/formatter.js`, `argparse/lib/argument_parser.js`, `js-yaml/bin/js-yaml.js`, `js-yaml/lib/js-yaml.js`, `metro-config/src/loadConfig.js`, and nested `cosmiconfig/dist/loaders.js`. Repeating the bounded precision probe against the pinned source establishes the `RangeError` but not a project attack path. A subsequent review must establish an untrusted format-string entry point, a call to the affected numeric formatter, and the process in which it executes before changing a disposition.
